## 2026-04-29 — Real-build trial across 3 frames; 10 runtime gotchas patched (v1.4.5)
- **Trigger:** User asked Claude to rebuild three full Pantheon-correct employee-management screens (Add Employee Personal Info, Role & Shifts, Leave Management) on the user's POS-Enterprise-Online file. The build succeeded but exposed 10 runtime gotchas that were not in v1.4.4 docs. All 10 patched here.
- **Findings (every one trial-verified, all rolled into SKILL.md / figma-authoring.md):**
  1. **`figma.currentPage` is a footgun.** Resolves to whatever page is active in the user's desktop, not the user's intended target. Always `getNodeByIdAsync(pageId)` and append there.
  2. **`layoutSizingHorizontal = "FILL"` requires append-first.** Set after `appendChild` to an auto-layout parent — never before.
  3. **`textStyleId` does NOT bind text color.** Text Styles carry typography only. Color must be explicitly bound to a `Text/*` semantic variable via `setBoundVariableForPaint` on the text's `fills`.
  4. **Variant axis docs were systematically wrong.** Trial-verified corrections in §1.6: Cards (`State` + `Type`, NO Density), Outline (different from Primary/Tonal — has `Icon Position` axis + `Show Icon=False/True`), Text Input (`Size/State/Type/Leading Icon/Trailing Icon/Supporting text/CTA`, NO Label axis), Radio (`Selected/State`, NO Size), Switch (Disabled is a Type, not a State), Badges (1 axis: Size only — no Accent), Chips (`State/Size/Shape/Icons` — Shape not Type, Icons plural, no Accent).
  5. **`Badges Size=Small` is a tiny dot indicator with no text. `Size=Large` is the labeled pill.** Use Size=Large for "Draft" / "Active" / status pills.
  6. **`get_design_context` requires the user to have a layer SELECTED in Figma desktop.** nodeId param alone errors. Use `get_metadata` for nodeId-driven inspection.
  7. **3-tier text-override fallback.** Pantheon components are inconsistent about how they expose text. Pattern: (a) componentProperties TEXT prop matching fuzzy name → (b) any componentProperties TEXT prop → (c) first descendant TEXT node mutated directly. Direct mutation by name regex was failing on Chips/Badges because their text nodes aren't named "Label."
  8. **Pantheon Cards is a TILE component, not a section wrapper.** Section wrappers should be styled auto-layout frames matching the Card spec (Surface/Primary fill + 1px Border/Primary stroke + Square/Medium radius), not literal Cards instances.
  9. **Pantheon Tabs labels can't be overridden via top-level `findOne`.** Each tab's text is in a nested sub-instance; would need per-sub-instance text-prop access. For now, tabs use Pantheon's default labels in generated work — flag in delivery footer.
  10. **Pantheon `Table` is a Slot-based container, not a sibling of Header/Body Block.** The Header Block + Body Block components are CELLS that go INSIDE Table's `Slot#2481:29` SLOT-typed property, not in a hand-composed auto-layout frame. Pattern documented in §1.6 Tables subsection (`tableInst.findOne(n => n.type === "SLOT")` → `slot.appendChild(row)`).
- **Files patched:** SKILL.md (§1.4 JS skeleton replaced with corrected version using all 10 patterns; §1.5 hard-gate checklist gained 3 new items; §1.6 Inputs/Containers/Tables tables rewritten with verified axes + Slot pattern + Cards-is-a-tile note + Badges Size=Small/Large clarification); references/figma-authoring.md (Scenario A skeleton fixed for `figma.currentPage` + page-id lookup; Common Defaults Outline button updated for new axes); plugin.json + marketplace.json bumped to 1.4.5; README.md changelog entry; this log.

## 2026-04-29 — Identity surfacing for shared-Cowork environments (v1.4.3, superseded by 1.4.4)
- **Trigger:** During the v1.4.2 trial, the test file landed in the MCP-auth'd account's drafts (`rutvij.parikh@petpooja.com`), but the user mentioned they personally use a different Figma account (`shrey.panchal@petpooja.com`). Petpooja's pattern is multiple teammates sharing a single Cowork install while each has their own Figma account. The Figma MCP is auth'd to one identity, which doesn't necessarily match whoever is using Cowork at the moment. Without surfacing this, files Claude creates can land in the "wrong" person's drafts and become inaccessible / invisible.
- **Patches applied:**
  - SKILL.md §1.3 step 1 (`whoami`): added an "Identity surfacing — required for shared-Cowork environments" block. - **Background context:** the old `/pantheon-bootstrap` (v1.2.x) used to programmatically compare the Figma identity against the Cowork email and warn on mismatches. v1.2.2/1.2.3 removed that check because it produced false positives (Cowork email, Figma email, SSO email, GitHub handle commonly differ for the same person). ## 2026-04-29 — Figma-authoring path corrected after live trial (v1.4.1)
- **Trigger:** User asked "is this a stable build, can we trial it?" before shipping v1.4.0. Live trial against the real Figma MCP found 4 critical bugs that would have made v1.4.0 fail in production. Patched same session.
- **Who:** Claude + Rutvij, Cowork session, real MCP calls against Pantheon (whoami, get_libraries, search_design_system × 13 component queries).
- **Bugs found and fixed:**
  - **Identifier conflation:** v1.4.0 used the file key `l8qALS4HQUMbSTyP8BTGRL` everywhere, but Figma's import API requires THREE distinct identifiers — file key (URL identifier), library key (`lk-` prefix, scopes search), and component key (40-char hex, the argument to `importComponentSetByKeyAsync`). v1.4.1 introduces SKILL.md §1.2 explicitly documenting all three with the canonical Pantheon values.
  - **Component imports were specified by node ID:** v1.4.0 told Claude to "insert by these IDs" in §1.5, but local node IDs are not importable across files. Replaced the §1.5 lookup table with §1.6 (verified componentKeys for 25+ Pantheon component sets, captured live via `search_design_system`). Local node IDs preserved alongside as inspection-only references.
  - **Button family structure:** v1.4.0 described Pantheon's Button as one component set with a `Hierarchy` variant axis. The reality (verified live) is 7 separate component sets — `Primary`, `Tonal`, `Outline`, `Text Buttons`, `Primary Icon Button`, `Tonal Icon Button`, `Outline Icon Button` — each with its own componentKey. §1.6 now reflects this.
  - **`use_figma` is a JavaScript executor, not a structured API:** v1.4.0 wrote pseudocode like `use_figma → insert_instance with variant_props…`. Fictional. v1.4.1 §1.4 has real JS skeletons using `figma.importComponentSetByKeyAsync`, `setProperties`, `figma.variables.importVariableByKeyAsync`, `setBoundVariableForPaint`, `figma.importStyleByKeyAsync`. Documents the gotchas the official Figma MCP tool description calls out (Inter style names with spaces, `setCurrentPageAsync`, getSharedPluginData over getPluginData).
  - **Tool parameter signatures:** `get_libraries` requires `fileKey`. `search_design_system` requires `query` + `fileKey` + uses `includeLibraryKeys` (a list of library keys, NOT file keys) to scope. v1.4.0 described both incorrectly. Fixed in §1.3.
  - **`/figma-use` skill prerequisite:** the official Figma MCP tool description says to load the `/figma-use` skill before any `use_figma` call. v1.4.0 didn't mention this. Added to SKILL.md §1 preamble and figma-authoring.md preamble.
- **Files patched:** SKILL.md (§1 entirely rewritten — §§1.1 non-negotiables, 1.2 three identifiers, 1.3 pre-flight, 1.4 insertion JS, 1.5 hard gate, 1.6 componentKey table, 1.7 anti-patterns, 1.8 missing-from-Pantheon, 1.9 delivery footer); references/figma-authoring.md (all 7 scenarios rewritten with real `use_figma` JS); hooks/pantheon-enforce.sh (reminder updated to cite componentKey-based imports); plugin.json + marketplace.json bumped to 1.4.1.
- **Library hygiene flag (Pantheon-side, not skill-side):** `search_design_system` returns junk components in the published library — `game_button_*`, `*_alt 1`, hundreds of icon symbols leaking into top-level component searches. Worth a one-time cleanup in Figma's Assets panel. Until then, the workaround in SKILL.md §1.3 step 3 (filter for `assetType: "component_set"` + `libraryName: "Pantheon"`) covers it.
- **Gaps remaining:** The `componentKey` table in §1.6 was captured 2026-04-29 via live MCP. If Pantheon component sets are republished (a name change, a structural rebuild), keys CAN change. `/sync-pantheon` should be extended to verify the table; for now, the MCP returns clean errors when a key doesn't resolve, so failures will be visible at runtime.
